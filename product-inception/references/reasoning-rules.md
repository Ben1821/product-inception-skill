# 判斷與提問規則

## 先找會改變的決策

先辨識使用者此刻要決定什麼，再找哪項資訊會讓答案不同。若已有可用的文件或觀察，先檢查來源、涵蓋情境、時間及是否有相反的證據。重複提問的成本通常高於先讀已有資料。

| 手上資訊 | 如何記錄 |
|---|---|
| 使用者確認的目標、限制或選擇 | 記為已確認決策，附確認來源與日期或版本。確認要做某功能只代表範圍共識 |
| 訪談、觀察、紀錄或原型結果 | 寫清誰、何時、實際發生什麼及涵蓋範圍。單次觀察可支持具體情境，能否推廣仍待驗證 |
| 對使用者行為、技術可行性、成本或因果的預期 | 標為待驗證假設，附現有依據與反例 |
| 模型提出的方案或取捨 | 標為 AI 建議，寫出適用條件和代價 |
| 資料互相衝突或尚未選擇 | 標為待決策，列影響與下一個查證點 |

「找不到資料」只支持目前的資訊缺口。若引用競品功能、服務限制或成本，附可取得的來源與適用條件。精確數字須能回溯來源，或清楚標為示例與待定提案。

## 讓一個問題帶來下一步

1. 先問具體行為，例如「上次準備考試時，你怎麼選到第一題？」視回答再追問放棄、替代方式或後果。
2. 功能背後有多種解釋時，說清哪種答案會改變優先順序。例如「主要摩擦發生在選題，還是看完結果後不知道怎麼重練？」保留使用者修正選項的空間。
3. 若是可逆決策且使用者要求先做草案，給一個明示的暫定假設，寫出它若不成立會影響哪段。重要前提互斥時，可交付條件式選項。
4. 挑戰提案時具體描述現況、可行替代方案與改變建議的條件。已有工具、人工代辦、維持現狀都可以是候選。依使用者真正面對的限制做取捨。

## 對假設設計最小驗證

- 優先處理「影響大、證據薄弱、改錯代價高」的假設。常見面向包括使用者是否需要、是否能使用、技術能否做到、團隊能否負擔，以及可能對人造成的影響。以文字理由描述排序即可。
- 把推測改成可被推翻的敘述。用「對哪群人、在什麼條件下、會出現什麼可觀察行為」描述。列出替代解釋，例如使用者完成任務可能是因主持人協助。
- 驗證要是建造者本人在期限內做得到的。學生或小團隊多半接觸不到目標產業的從業人員或內部資料，此時改用公開案例回放、公開文件、模擬資料或相近背景的人，並寫明替代能回答什麼、不能回答什麼。查不到之前先給預設做法，讓開發不必停下來等。
- 方法對應未知。理解過去行為用訪談或觀察。檢查流程摩擦用任務原型。驗證技術限制用有時限的 Spike 或 PoC。檢查實際使用結果用定義清楚的試用或事件紀錄。
- 寫下假設、來源、測試對象或環境、信號與判讀、負責人或待分派、回看時點。明定支持時如何推進、反證時如何調整、證據不足時還要補什麼。若門檻仍待定，先保留相關承諾。

交代可供審閱的結論、依據、取捨與未知即可。決策改動時，指出受影響的既有文件和工作項目。
