# Architecture Exploration

## 先找會左右選型的條件

從核心流程、團隊能力、資料敏感性、外部整合、可用性、效能及預算抽出相關的驅動因素。用「在什麼情境、系統要如何反應、怎麼檢查」描述品質屬性。尚未確認的流量、成本、延遲或服務限制標為待驗證。

比較能滿足已知限制的實質選項。依專案考慮既有方案、簡單部署、託管服務或獨立執行邊界。每案交代如何滿足驅動因素、實作與維運成本、失敗影響、切換難度，以及缺少的證據。只保留有意義的候選；若只有一案可行，寫出淘汰條件。對已定案的選擇，可在新限制或證據出現時重評。

## 用 C4 回答具體問題

- **System Context**以目標系統為中心，呈現直接互動的使用者角色、外部系統與關係用途。用來對齊責任與外部依賴。
- **Container**聚焦同一系統的可執行應用、服務或資料儲存，標示用途、主要通訊與資料流。此處的 container 是 C4 的抽象層級，可能以多種方式部署。把外部服務放在邊界外，資料跨信任邊界時標出主要資料類型及相關控制。
- 只畫能回答當前問題的層級。若關鍵疑問是一次請求如何跨容器、發生何種失敗，再補循序圖或短的資料流敘述。若使用文字，仍應標示邊界、責任和有方向的關係。

## 留下可重評的決策與驗證

對影響邊界、資料所有權、重要依賴、維運責任或難以逆轉的選擇建立 ADR。用一份 ADR 說明一個決策，包含背景、限制、替代方案、決策或暫定提案、理由、正負後果及重評條件。狀態可用提案、已採納、已取代。後續改選時連到取代它的 ADR。

Spike 或 PoC 聚焦一個會改變決策的技術未知。寫下要回答的問題、測試環境、資源上限或回看時點、可接受結果及失敗後的替代。若公開服務需通過安全或權限驗證，把發布阻礙寫進 MVP 規格和待辦。概念驗證的結果僅適用於實際測試條件。
