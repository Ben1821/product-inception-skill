# User Story Mapping

1. 選定一個角色與情境，先寫開始條件和可觀察的成功結束狀態。
2. 橫向排列使用者敘事的活動骨架，例如找題 → 作答 → 提交 → 理解結果。每欄向下展開任務、變體和可交付的故事。
3. 在會中斷旅程的地方記下前置條件與替代路徑。依風險描述影響最大的例外，例如資料不存在、服務逾時或使用者權限不足。只有會影響首版成果或最低保障的例外才需要進首版。
4. 用一條跨越各關鍵活動的發布切線標示「誰能完成什麼」。以具體案例走一遍，再試一次最重要的例外。技術骨架可以串起端到端，但交給目標使用者前仍須檢查體驗與最低門檻。

故事可用角色、行為、結果表示。技術 Spike 或共用品質工作直接寫目的及可驗證交付。單一路徑的小工具可用一行旅程和一張表；涉及不同角色、例外或多次發布時再展開。故事地圖可顯示旅程與發布順序，需求是否真有價值仍看探索證據。
