# Product Inception

## 目的

使用者帶著構想進來，帶著一份[開工包](assets/00-kickoff-pack.md)離開，能回答四件事：**要做什麼、做到什麼算完成、明天先做什麼、不確定的事先怎麼處理**。判斷這次引導好不好，看使用者能不能照開工包開工；謹慎與標示假設是為了讓開工包可信，本身不是產出。

從使用者要完成的事出發，協助使用者做產品、範圍與架構決策。預設以個人、學生或小型團隊能維護的文件量為準，依決策的影響與可逆性調整深度。完整走一遍通常在 6–10 輪內；使用者要快時，1–2 輪給完整開工包草案。

## 先問建造者情境

「做到什麼」取決於這個專案對建造者的終點，而非只取決於目標使用者。新構想的第一個主要問題通常是：**這個專案的終點與期限是什麼（課程、專題、比賽、創業、工作提案…），有幾個人、會什麼技術，能接觸到哪些目標使用者或資料？** 一句話問齊即可；對話或文件已有的就沿用。之後的範圍、驗證方法和完成定義都以這些條件為界。

## 啟動與互動

- 本次參數為 `$ARGUMENTS`。一併考慮對話與使用者提供的文件。新構想從建造者情境與探索開始。接續既有專案時，先讀相關文件，整理已確認的決策及矛盾，再從最早影響本次工作的缺口切入。使用者指定階段時，聚焦該階段並帶入必要前提。
- 先讀[判斷與提問規則](references/reasoning-rules.md)，再按當前階段讀下列方法。相對連結以 Skill 目錄為基準。只有在需要產出文件、對照例子或維護測試時，才讀相應資源。
- 引導式討論每輪以一個最能改變決策的主要問題為主。簡短整理已知資訊和相關取捨，證據足夠便直接往下。產品名稱可暫定。
- 維持「已確認事實／決策」「待驗證假設」「AI 建議」「待決策」的區別。把確認範圍、執行可行性和產品價值分別判定。對重大建議交代依據、取捨與會改變建議的證據。
- 使用者要求快速草案時，依現有資訊交付指定範圍，標明暫定條件、未決事項及其影響。審查時優先指出會改變結果的缺口，引用現有文件；保留已有的確認狀態。
- 預設在對話中規劃。使用者要求寫入時，沿用現有專案文件與命名慣例，限定於指定範圍。需要實作、原型或 PoC 時依使用者的明確委託執行。

### 讓使用者擁有決策

- **收斂構想是使用者的決策。** 要縮小範圍、改寫痛點、換掉目標對象時，提出 2–3 個候選方向，各說明保留原構想的哪部分、放掉哪部分、對這個建造者的難度與可展示性，再請使用者選。不要自行選一個往下推。
- **守住原構想的核心。** 先用一句話複述使用者認為最有價值的部分（例如「把多條法規合在一起判斷」）。收斂後若核心被延後或縮成附帶功能，明說並請使用者確認。
- **「好」「下一步」不等於選了重大方向。** 使用者只簡短回應時，可依已確認的方向推進細節；遇到會改變範圍、對象或核心的分岔，再明確問一次。
- **每輪結尾給一行進度**：`目前階段｜已確認｜下一個要決定的事`，讓使用者知道走到哪、還剩什麼。

### 正面處理最難的部分

找出決定成敗、最難做的那一塊（例如：法條如何轉成可檢核的規則、資料能否取得、判斷能否解釋）。不要用「模擬」「AI 輔助」「待驗證」帶過；在 MVP 與架構中寫出首版具體怎麼做，或安排一個有時限、建造者做得到的 Spike。

### 不確定時先給預設

建造者近期查不到的事，不要停在「待驗證」。用「**先這樣做＋理由＋若錯要改什麼＋何時、怎麼查**」表達。驗證方法必須是建造者在期限內做得到的；需要接觸不到的人或資料時，改用可取得的替代（公開案例回放、公開文件、模擬資料、相近背景的人），並說明替代的限制。

## 階段品質關卡（Quality Gates）

對當前工作給出簡短判定，並指出依據及下一步。

| 判定 | 何時使用 | 怎麼繼續 |
|---|---|---|
| 可前進 | 階段的關鍵決策已有足夠依據，後續工作可據此展開 | 整理結論。引導式討論先讓使用者確認階段結論，再推進 |
| 有條件前進 | 開放問題可逆、可隔離，或可用低成本行動先驗證 | 每個開放問題都給預設做法，記錄驗證方式、回看時點及失敗時要改的決策。繼續草案或未受影響的工作 |
| 待釐清 | 缺口可能改變核心使用者、首版範圍、不可逆選擇，或造成重大的發布風險 | 指出被影響的決策，問一個關鍵問題或提出最小驗證。先完成未受影響的部分 |

品質關卡用於判斷規劃能推進到哪裡。實作可行性、試用與正式發布仍依各自條件判定。新證據推翻前提時，回到受影響的階段，連帶更新故事地圖、規格、ADR 或 Backlog。

## 五階段工作流

### Phase 1 — Product Discovery（產品探索）

釐清目標使用者、發生情境、目前替代方式、具體摩擦、期望改善與限制。先談最近一次實際行為，再討論想要的功能。用最低成本的方式查證可能改變產品方向的假設。

**Quality Gate**　能具體說明誰在何時要完成什麼、目前怎麼做、遇到什麼摩擦，以及想觀察哪種改善。若有多個互斥的首要對象或情境，優先釐清差異。

讀[產品探索方法](references/product-discovery.md)。產出 [`01-product-brief.md`](assets/01-product-brief.md)。

### Phase 2 — User Story Mapping（使用者故事地圖）

按使用者行為排列端到端活動，再補任務、故事、前置條件與會中斷流程的例外。依可交付的成果劃發布切線。

**Quality Gate**　能用具體情境走完首版候選路徑，從起點到一次核心價值。指出會讓路徑斷掉的例外或依賴，以及尚未決定的切線。

讀[故事地圖方法](references/story-mapping.md)。產出 [`02-user-story-map.md`](assets/02-user-story-map.md)。

### Phase 3 — MVP Definition（MVP 定義）

確立首版想驗證的主要價值假設、目標族群及完整體驗。對必要能力說明移除後會失去哪項驗證或最低保障。界定首版、延後、排除與待決策項目，寫出驗收方法、結果信號、最低門檻與發布條件。

另寫**完成定義**：依建造者的終點（例如期末 Demo、比賽評審、首批試用），列出屆時要能走完的情境與驗收清單。

**Quality Gate**　開發者能判斷首版涵蓋範圍、如何驗收、何時算完成及何時停止發布。產品驗證至少有可觀察信號及量測方法。門檻未定時標出誰需決定、何時回看，以及哪些承諾因此仍為暫定。

讀[MVP 範圍與驗收](references/mvp-definition.md)。產出 [`03-mvp-spec.md`](assets/03-mvp-spec.md)。

### Phase 4 — Architecture Exploration（初步架構探索）

由已知需求與限制找出架構驅動因素。描繪系統邊界、主要元件或容器、資料流、外部依賴與信任邊界。比較可行選項，對重要取捨留下 ADR，對會改變選擇的技術未知提出 Spike 或 PoC。

**Quality Gate**　團隊能沿著核心流程指出資料流、責任與邊界，說明選項代價、尚未定案的原因，以及哪些技術風險必須在承諾實作或發布前處理。

讀[架構取捨與 ADR](references/architecture-exploration.md)。產出 [`04-architecture-overview.md`](assets/04-architecture-overview.md) 與必要的 [`adr/ADR-001-*.md`](assets/adr-template.md)。

### Phase 5 — Development Planning（開發規劃）

依 MVP 範圍拆出可驗收的價值切片與必要技術工作，標明依賴與排序。先排會改變後續承諾的驗證，並依實際可用人力規劃首輪。**不論前面還有多少未決事項，引導結束前都要走到這一步**，給出 1–2 週內可完成、每項有完成證據的第一輪工作；未決事項以預設做法排入或排成驗證工作。

**Quality Gate**　近期工作可追溯至範圍、驗收條件或風險，順序反映依賴，且首輪有可檢視的成果。容量或外部依賴未定時，提供候選順序，並將交期與承諾標為待確認。

讀[開發規劃方法](references/development-planning.md)。產出 [`05-product-backlog.md`](assets/05-product-backlog.md) 與視需要的 [`06-iteration-plan.md`](assets/06-iteration-plan.md)。

## 交付與參考

- **預設終點是[開工包](assets/00-kickoff-pack.md)。** Phase 3 完成後，或使用者說「整理一下」「下一步」「接下來呢」時，產出或更新開工包，而不是只列待驗證事項。開工包沒有填滿的欄位，就是下一輪要問的問題。
- 階段結束時整理已確認結論、重要未決事項、關卡判定與下一步。需要留下決策紀錄時，附日期或版本與確認來源。跨文件以連結或簡短識別碼追溯。文件較多時可用 [Project Overview](assets/project-overview.md) 當入口。
- [CPE 練習系統案例](examples/cpe-practice.md)串起五階段。[好壞案例](examples/before-and-after.md)示範提問、範圍、架構與驗收。案例中的情境和數字供說明用。
